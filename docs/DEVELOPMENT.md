# 개발 경위와 판단

이 프로젝트는 개인 투자 리서치에서 시작했습니다. 아래 순서는 작성자의 실제 개발 경위에 따른 것이며, 두 시스템의 코드가 순서대로 교체된 하나의 버전이라는 뜻은 아닙니다.

## 1. etf-radar와 수동 GPT 리서치

먼저 `etf-radar`를 만들고 후보를 선별한 뒤 GPT에 직접 조사를 요청했습니다. 직접 사용하는 과정에서 반복적인 입력과 결과 정리가 번거로웠습니다. 해결하고 싶은 문제는 리서치 과정을 반복 실행하고 결과를 일관되게 남기는 것이었습니다.

## 2. API 기반 시스템을 별도로 개발

수동 작업에 API를 적용하고 싶어 새로운 시스템을 만들었습니다. 이 저장소는 그 시스템의 공개 버전입니다. Quant 후보 선별, Gemini 조사, GPT 구조화 판단, 제약 적용과 기록을 연결합니다.

현재 코드에서는 모델의 자유로운 설명만으로 화면 수치를 결정하지 않습니다. 허용된 종목·행동·단위·순위를 검증하고, 제약 적용 후 결과를 `effective`로 저장합니다. 실패한 단계를 완료된 AI 판단으로 표시하지 않는 것도 중요한 경계입니다.

공개 과정에서는 개인 계좌·운영 DB·실제 LLM 응답을 제외하고 합성 데모를 추가했습니다. 데모는 시스템의 동작을 빠르게 확인하기 위한 별도 진입점입니다. API 기반 개발 자체가 처음부터 합성 데모만을 목적으로 한 것은 아닙니다.

## 3. 기존 로직에 자동화·검증을 다시 보강

작성자는 개인 운용에서 `etf-radar` 로직의 결과가 더 좋다고 느꼈고, 현재 그 프로젝트도 다시 수정하고 있습니다. **이 경험은 동일 기간·종목·자본·거래비용을 맞춘 비교 실험 결과가 아닙니다.** 기존 로직의 우월성이나 API 도입의 수익률 효과는 아직 입증하지 않았습니다.

현재 방향은 기존 로직을 활용하면서 반복 리서치를 자동화하고, 계좌 입력의 불완전성과 단계 간 판단 변경을 검증하는 것입니다. 별도 프로젝트에서 관찰한 문제와 확인한 코드 범위는 [문제 해결 사례](CASE_STUDIES.md)에 기록했습니다. 그 소스 전체를 이 저장소에 합치지는 않았습니다.

## 현재 설계의 선택과 대가

아래는 현재 구현에 대한 판단입니다. 모든 선택을 과거에 정량 비교한 것처럼 제시하지 않습니다.

| 선택 | 얻는 것 | 남는 비용·제약 |
|---|---|---|
| 후보 선별과 LLM 리서치를 단계로 분리 | 어느 단계에서 판단이 바뀌었는지 추적 | 호출·저장·실패 처리의 복잡성 증가 |
| 구조화 출력 뒤 코드로 제약 적용 | 설명과 무관하게 종목·단위의 범위 검증 | 구조가 맞아도 투자 근거는 틀릴 수 있음 |
| 미확정 입력을 `null`로 보존 | 모르는 잔고를 현금이나 미보유로 오인하지 않음 | 실행 가능한 배분을 제공하지 못하는 경우 발생 |
| 주문 실행을 시스템 범위에서 제외 | 리서치와 검토에 집중 | 주문 체결·슬리피지·실현 성과는 검증하지 못함 |
| 키 없는 합성 데모 제공 | 운영 자료 없이 판단·저장·복원을 재현 | 실제 모델·API의 응답 품질은 보여주지 못함 |

복잡한 시스템을 만들었다는 사실과 더 좋은 투자 판단을 했다는 사실은 다릅니다. 다음 평가는 수익률뿐 아니라 수작업 개입, 실패율, 판단 변경, 입력 완전성, 비용을 함께 측정하는 방향이어야 합니다. [평가 계획과 현재 증거](EVALUATION.md)

## 작성자 역할과 AI 활용

- **작성자:** 개인 리서치의 불편 발견, 수동 작업의 API 전환이라는 목표 설정, 실제 사용 경험에 따른 개발 방향 선택.
- **AI 도구 활용:** 코드 구현, 구조 검토, 오류 수정, 테스트 작성·실행 보조, 문서 정리에 GPT와 AI coding tools를 폭넓게 사용했습니다. 모든 코드를 독립적으로 직접 작성했다는 의미로 제시하지 않습니다.
- **결과의 책임 범위:** 구현된 내용과 실행한 검증을 코드·테스트·기록으로 제시합니다. 확인하지 않은 투자 성과, 조직 도입 효과, 사용자 수나 업무시간 절감 수치는 제시하지 않습니다.

이 작업은 개인 프로젝트입니다. 금융회사 내부 시스템에 실제 도입하거나 조직 차원의 AI 거버넌스를 운영한 경력으로 표현하지 않습니다. 업무 적용 관점에서는 입력 품질, 결과 추적, 실패 처리, 검증 수준의 표시를 고민한 사례로 볼 수 있습니다.
